# 工作流：七个阶段，三道闸门

这份文档定义人和 AI 怎么一起把一份汇报做出来。它规定的是**先后顺序、每一步的产物、谁说了算**，不规定讲什么、画什么。

```
 入口            S0 立项 ──G0──▶ S1 取材 ──▶ S2 分镜 ──G1──▶ S3 搭建 ──▶ S4 自检 ──▶ S5 评审 ──G2──▶ S6 交付
 new / adapt     brief.md        sources.md   storyboard.md    deck.html    review 报告   review.md        dist/*.html
 / revise                                          ▲                ▲                        │
                                                   └── 改"要讲什么" ─┴── 改"怎么表现" ◀──────┘
```

每个 deck 是 `decks/<name>/` 下的一个文件夹，五个文件贯穿始终：

| 文件 | 回答的问题 | 谁写 | 谁定 |
|---|---|---|---|
| `brief.md` | 给谁讲、讲多久、长什么样、哪些东西不要 | AI 起草，人改 | 人 |
| `sources.md` | 有哪些材料，哪个数字以哪份材料为准 | AI 整理 | 人指定权威来源 |
| `storyboard.md` | 每一页只讲哪一件事、靠哪张图讲 | AI 起草，人改 | 人 |
| `deck.html` | 幻灯片本身 | AI | 人验收 |
| `review.md` | 每一轮改了什么、还欠什么、哪些是 AI 自己推的 | 两边都写 | — |

---

## 入口

三个入口，只是起点不同，之后走同一条流程。每个入口在 `entry/` 下有一份可以直接交给 AI 的启动说明。

| 入口 | 什么时候用 | 从哪开始 |
|---|---|---|
| **new** | 只有主题和一堆材料 | S0 |
| **adapt** | 已经有一份报告、网页、旧 PPT、别的风格的 HTML，要改造成标准 deck | S0（brief 从旧稿反推），S1 把旧稿登记为来源 |
| **revise** | deck 已经存在，要逐页修改 | S5 |

---

## S0 立项 → `brief.md`

AI 先读材料，再起草 brief，人确认。brief 里要定下来的是**整份 deck 的口径**，这些东西如果不事先定，会在每一轮评审里反复被推翻：

- 听众是谁、他们关心的问题是什么、讲多久
- 幻灯片语言，和**对话语言**（两者可以不同，分开写）
- 标题风格：`topic`（几个词说明这页在讲什么）还是 `claim`（一句结论）
- 扉页和页面上放什么、不放什么（姓名、单位、页脚、章节标签）
- 记号约定（例如"相对量一律写成 I/I₀ 这样的显式比值，不用单字母代号"）
- 参考样本：一份你认可的旧 deck，或一句风格描述
- 对默认规则的豁免（见 [contract.md](contract.md) 的"默认"一层）

**闸门 G0**：人读完 brief 说"可以"。不需要完美，之后随时能改，但改 brief 意味着整份 deck 要重新过一遍。

## S1 取材 → `sources.md`

把所有材料登记成带编号的来源（`S1`、`S2`…）：文件路径或链接、它是什么、**它对哪些内容有最终解释权**。

三条硬规则：

1. **人指定的来源优先于 AI 自己找到的。** 仓库里的旧数据、AI 从日志里统计出来的数字，都不能顶替人说"以这个为准"的那份。
2. **来源之间对不上，就停下来问**，把两个数字和各自出处并排列出来，不要自己挑一个。
3. **拿不到的材料登记为"缺"**，在 deck 里留占位，不要凭印象重画或编数。

## S2 分镜 → `storyboard.md`

这是整个流程里最值钱的一步。每一页一个条目：

```markdown
## tradeoff · approved
- point:   两种方案没有固定的赢家，参数一变排名就交换
- visual:  散点图。x = 每次操作的损失，y = 每秒完成的轮数；滑块调读出时间
- source:  S4（13 组模拟结果），S5（参数范围，缺）
- interact: 一个滑块；点任意一个点打开该方案的回放
- comment:
```

- `point` 是这一页**唯一**要让听众带走的东西，一句话。写不出一句话的页应该拆或者删。
- `visual` 写清楚图的类型、坐标轴含义、图上要标出什么。
- 条目标题是页面的**稳定 id**，不是页码。页码会变，id 不变。之后所有讨论都用 id 指页。
- 分镜阶段只改这份文档，不写 HTML。改一句话比改一页便宜两个数量级。

AI 在这一步有**提案权**：可以提出合并、拆分、调换顺序、换一种图，但要写在分镜里让人看到，不能在搭建时悄悄做。

**闸门 G1**：人逐条过 `point`，把状态改成 `approved`、`cut` 或写 `comment`。只有 `approved` 的页进入搭建。

## S3 搭建 → `deck.html`

AI 按 [contract.md](contract.md) 和 [design.md](design.md) 把 `approved` 的页做出来。

- 一页围绕一张图。图能自己画就自己画，不要留"此处应有图"。
- 每个数字、每张图标注来源（`data-src="S4"`）。AI 自己推出来的值标 `data-derived`，没核实的标 `data-unverified`，等材料的标 `data-placeholder`。
- 版式、配色、交互方式是自由发挥的地方，见 design.md 的"发挥空间"。

## S4 自检

交给人之前，AI 必须自己做完这三件事并如实报告：

1. 打开 deck，运行 `DeckReview.run()`（或按 `R`），**error 清零**；warn 要么修掉，要么在页面上用 `data-allow` 豁免并在 review.md 里说明理由。
2. 每一页截图看一遍；每个按钮、滑块、播放器实际操作一遍。
3. 换一个窗口尺寸（缩小、窄屏）再看一遍。

没做的检查要明说"没做"，不要用"应该没问题"带过。

## S5 评审 → `review.md`

AI 交付时，在 `review.md` 里开一轮记录，固定三段：

- **改了什么**：按页面 id 列。
- **没做到什么**：拿不到的材料、没验证的部分。
- **需要你确认的**：自检报告里所有 `open` 项——AI 自己推的结论、读图读出来的数、对人的话的理解。

人按页面 id 写意见。AI 先判断每条意见属于哪一类，再动手：

| 意见类型 | 例子 | 回到哪 |
|---|---|---|
| 要讲的东西不对 | "这页没讲明白为什么这样构造是对的" | S2：先改分镜的 `point`，确认后再做 |
| 表现不对 | "字太小""图注看不清""曲线太尖看不出东西" | S3：直接改 |
| 口径变了 | "全部改成英文""标题不要结论句" | S0：改 brief，再全局应用 |
| 指代不清 | "P5 没必要" | 先用 id 复述一遍再动手，尤其是删除 |

**一条意见同时指向很多页时**（"整体没把我想表达的东西讲清楚"），不要直接重做，先把每页的 `point` 列成表让人逐条改——这是分镜的本职。

**闸门 G2**：人说"可以了"。

## S6 交付

```
python tools/build.py decks/<name>
```

产出 `dist/<name>.html`：样式、脚本、数据、图片全部内联的单个文件，离线可用，可以直接发给别人或托管。打印即得 PDF（一页一张）。

## 谁说了算

| 事项 | 人 | AI |
|---|---|---|
| 讲什么、不讲什么 | 决定 | 提案 |
| 每页的 `point` | 决定 | 起草 |
| 哪份材料为准 | 决定 | 登记、发现冲突时上报 |
| 用什么图表达 | 否决权 | 决定并执行 |
| 版式、配色、交互 | 否决权 | 决定并执行 |
| 契约里的硬规则 | 可以在 brief 里改 | 必须遵守 |
| 删页、删内容 | 决定 | 执行前用 id 复述 |
| "这样对不对" | 最终判断 | 给出证据和不确定之处 |

一句话：**人负责判断，AI 负责劳动和举证。** 流程的作用是让判断发生在便宜的地方（一句话的 `point`），而不是昂贵的地方（做完的十六页）。
